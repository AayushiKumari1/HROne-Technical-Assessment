# REVIEW.md

These are the problems I found in the starter `app/main.py`. For rows 1 to 3 I called the starter functions directly and compared the results with the rules in the spec. For the rest I found the problem by reading the code and checking it against `openapi.yaml` and `DATA_MODEL.md`.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | It rounds down to whole minutes and then checks `> 10`, so a punch at 09:40:01 counts as 0 late minutes when the spec says 10. It also uses the punch's own date and timezone instead of IST, and it ignores overnight shifts. | For a 09:30 shift, 09:40:00, 09:40:01 and 10:15:59 gave 0, 0 and 45. They should give 0, 10 and 45. | I work in IST, compare the gap in seconds, apply the grace period only when it is more than 600 seconds, and measure from the attendance date's shift start. |
| 2 | `compute_work_hours` | Python's `round()` on a float is not half-up. | A 450-second shift is 0.125 hours. The starter returned 0.12, but R4 needs 0.13. | I use `Decimal` with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` | There is no 30-minute minimum, so 15 minutes of overtime is counted. The shift end is put on the same date, which is wrong for overnight shifts. A naive and an aware datetime can't be subtracted. | Punching out at 18:45 for an 18:30 shift end gave 15 instead of 0. A naive `punch_out` raised `TypeError`. | The shift end is built from the shift's start date (next day for overnight shifts), times are aware UTC, and overtime only counts when it reaches 30 minutes. |
| 4 | `EmployeeIn` | Every field is a plain `str`, so a bad `emp_code`, a bad email, a time like "25:99", equal shift times or a fake date are all accepted. | POST /employees with `emp_code` "X1" is accepted because nothing checks it. | Pydantic patterns and length limits, a real-date check, and a check that `shift_start` and `shift_end` differ. Bad input returns 422. |
| 5 | `PunchInIn` | `status` can be any string. `punched_at` accepts seconds, floats and strings, and `if body.punched_at` treats 0 as "not given". | Status "FOO" or a timestamp in seconds goes straight through. | `status` is limited to PRESENT, WFH and ON_DUTY, `punched_at` must be an integer in epoch milliseconds in a sensible range, and I check `is not None`. |
| 6 | `health` | It always says ok and never talks to MongoDB. | Stop MongoDB and `/health` still returns ok. | It pings MongoDB and returns 503 if that fails. |
| 7 | `create_employee` | It checks for a duplicate and then inserts, with no unique index, so two requests at the same time can both succeed. It also stores a naive local time and returns `created_at` as a datetime instead of epoch milliseconds. | Send the same `emp_code` twice at once. Look at the type of `created_at` in the response. | A unique index on `emp_code` plus catching `DuplicateKeyError` (409). `created_at` is stored in UTC and returned in milliseconds. |
| 8 | `list_employees` | `skip = page * page_size` skips the first page. `total` counts the whole collection and ignores the department filter. There is no sort, and `page` and `page_size` are not validated. | Page 1 starts at the 21st employee. `total` stays the same when you filter by department. | `skip = (page - 1) * page_size`, `total` uses the same filter, results are sorted by `emp_code`, and `page` / `page_size` are validated (`page_size` max 100). |
| 9 | `punch_in`, employee lookup | An unknown `emp_code` gives `emp = None`, and `emp["shift_start"]` raises `TypeError`, so the API returns 500. | POST punch-in with a code that doesn't exist. | Return 404 when the employee isn't found. |
| 10 | `punch_in`, date and time | `fromtimestamp()` and `.date()` use the server's local time, not IST, and the overnight rule (R1) isn't applied. | A punch close to midnight IST ends up on the wrong date when the server isn't in IST. | Times are stored in UTC and the attendance date comes from IST and the shift (`attendance_date_for_punch`). |
| 11 | `punch_in`, race | It checks first and inserts second, so two simultaneous punch-ins can both pass the check. | Send two identical punch-ins at the same moment. | A unique index on (`emp_code`, `date`) and a catch for `DuplicateKeyError` (409). |
| 12 | `punch_in`, response | It returns an `id` built from `_id`, which the contract forbids, and raw datetimes instead of epoch milliseconds. | Look at the response of a punch-in. | One `api_log` function drops `_id` and converts times to milliseconds. |
| 13 | `list_attendance` | It loads every record into Python, then sorts and slices there. The sort is by `date` only, with no `emp_code` tiebreaker. | It would be very slow on 100k records, and the order of records on the same date isn't stable. | Filtering, sorting by (`date` desc, `emp_code` asc), counting and paging all happen in MongoDB, backed by an index. |
| 14 | `list_attendance`, contract | It returns `id` and raw datetimes, doesn't fill in `half_day`, `history`, `late_minutes` and `overtime_minutes` for legacy records, and doesn't validate `page`, `page_size`, `status` or `date_from > date_to`. | Compare the output with the legacy sample record in `DATA_MODEL.md`. | `api_log` fills the defaults, and the validation returns 422. |
| 15 | Startup | No indexes are created, so nothing guarantees uniqueness and queries scan the whole collection. | Check the indexes: only `_id` exists. | The indexes are created at startup and are safe to run again. |

## Things I looked at and decided were fine

- `load_dotenv()` doesn't override variables that are already set, so the real environment wins, which is what the spec wants.
- Regular `pymongo` inside plain `def` endpoints is fine because FastAPI runs those in a thread pool.
- The `{"_id": 0}` projection in `list_employees` correctly hides the internal id.
- Status 201 on the create endpoints is correct.
